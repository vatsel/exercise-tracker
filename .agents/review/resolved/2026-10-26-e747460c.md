## Changes

- **New "Request-time values" bullet after Dev server: `connection()` before `new Date()`.**
  - Detour: the agent removed `await connection()` from `src/app/page.tsx`, despite the comment above it
    ("Today's date must be read per request"). It assumed that awaiting `searchParams` made the page render
    per request. The user then hit "Blocking Route: Next.js encountered the unstable value `new Date()`
    while prerendering" at `todayDate (src/lib/workouts.ts:38)`. In that version `searchParams` was already
    awaited before `todayDate()`. The user had to paste the error, and fixing it took another turn.
  - Verified fact: `next.config.ts` sets `cacheComponents: true` (and `partialPrefetching: true`).
    The bundled guide `node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md` ("Random values
    and timestamps") says to call `connection()` before such values. The current `page.tsx` has
    `await connection()` before `todayDate()` again.
  - Verified in: `next.config.ts`, the caching guide, `src/app/page.tsx` and `src/lib/workouts.ts`.

- **Firefox DevTools gotchas, added to the "Check UI changes in a browser" bullet.**
  - Detour: while testing the date picker, `fill_by_uid(…, "2099-01-01")` left the field at `9010-09-20`.
    The agent reloaded, filled it again with the same result, then retried with `01012099`. Separately,
    `accept_dialog` after clicking **Delete exercise** failed ("Failed to accept dialog"), because the
    `confirm()` had already returned Cancel. The agent then stubbed `window.confirm` via `evaluate_script`.
    In total that was about four extra calls. The app has both a date input and a delete confirm, and
    the rule above it now requires a browser check, so later sessions will run into both.
  - Verified fact: I reproduced both today on a standalone `data:` page in Firefox (not the app, to avoid
    autosaving to the live DB). Filling `2099-01-01` gave `.value` `9010-09-20`. After a button's
    `confirm()`, `accept_dialog` errored and `confirm` had returned `false`. Filling `01012099` gave
    `2099-01-01` on an empty field but `""` on one that was already filled. That's why the line says to
    read `.value` back instead of prescribing a digit order.
  - Verified in: the firefox-devtools MCP (`fill_by_uid`, `accept_dialog`, `evaluate_script`) and
    `src/components/WorkoutForm.tsx` (`<input type="date">`, delete confirm).
